MEASUREMENT · PROMOTION GATE

Shadow evaluation

Every GTM system accumulates changes nobody measures — someone raises a threshold because the list "felt noisy", someone widens a window because a tier looked thin. This replays two configs over the same recorded rows and answers three questions: what moves, what leaves, and what did the rows that left ever produce.

Its verdict is a refusal as often as an approval. It blocked a config change that saved 43 cents and would have dropped three leads with verified work emails.

How I build

Four things I'd rather be held to than a feature list.

Agents where it's open-ended, code where it repeats

Researching an undocumented market needs a model. Enriching 500 rows the same way every night does not — and shouldn't cost tokens or drift. The pipeline has no model in it.

Cost is an invariant, not a dashboard

Per-run and per-day caps live in code and throw. Reservation is atomic, so concurrent workers can't slip through the gap between checking a budget and spending it.

Measure the change, don't ship the vibes

A change that "feels tighter" is a hypothesis. Replaying it against real rows, and labelling outcomes when you have them, is the only thing that makes it a decision.

If it isn't verifiable, it's marketing

82 assertions over the real pipeline, structural tests for every retry and payload, deterministic replays, and CI on every push. No mocks standing in for the thing itself.

Background

The systems in this repo are portfolio work — built to think the problem through end to end, not a record of production deployments. I'd rather say that plainly than let a demo imply something it isn't. What is from production is the discipline: this is written the way I'd write infrastructure, because that's the background I come from. Attio is the CRM I've worked in, and the one this pipeline is designed around. The rest of the adapters were a deliberate exercise — I wrote them rather than claim familiarity, and kept notes on what actually bit: HubSpot's domain isn't a unique key, Salesforce can only upsert on a custom External ID field, Lemlist's add-lead creates but never updates, and TitanX is a scoring API rather than a dialer.
